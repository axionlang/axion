# Design plan — reclaiming polymorphic container payloads

**Status:** proposal. **Goal:** close a real, latent leak — a generic container of
heap elements (`List String`, `List (Maybe a)`, `List P`, a tree of records, …)
leaks its **elements** when it dies. Confirmed: `List P` (record `P`) → `4 allocs,
2 frees` (the 2 `Cons` cells are freed, the 2 `P` payloads leak). It is a leak
(safe), but it breaks the GC-free promise ("we reclaim everything") for generic
containers.

## 1. Why it happens (the root cause)

Axion values are uniformly **i64**. A heap object has only a **size header**, no
type tag — so at runtime you cannot tell whether an i64 field is a pointer or an
`Int`. The generated destructor `axion_drop_List` (for `data List a = Nil | Cons a
(List a)`) frees the spine (each `Cons` cell + the recursive tail) but the element
field `a` is **`Type::Var("a")`** — `RecordInfo::field_is_heap`/`con_drop_slots` only
record fields whose `head_con()` is a concrete `data` type, so the polymorphic `a`
is never a drop slot. When `a` is instantiated to a heap type, the payloads leak.

There is **no runtime shortcut** (can't discriminate i64 pointer vs Int without a
tag). The two principled fixes are **monomorphization** (Rust's way — generate a
per-instantiation destructor) or **drop-witness passing** (dictionary-passing a
"how to drop `a`"). Axion already monomorphizes typeclasses, so **monomorphization**
is the aligned choice.

## 2. Success criteria / non-goals

**Must hold:** a dropped generic container reclaims its elements (`allocs == frees`),
across `--dev`/`--release`, verified by ASan/LSan; semantics unchanged (GHC oracle);
no new double-free (the drop path is memory-safety-critical — this is the gate).

**Non-goals (honest boundary):** full generic-**function** monomorphization
(specializing `length :: List a -> Int` per element type) is out of scope — it is a
huge feature. The plan targets the case where the **concrete element type is known
at the drop site** (which is the common one: a container is *owned and dropped*
where its concrete type is known; generic functions that merely *borrow* it don't
drop it). A generic function that **owns** (`%1`) and drops a polymorphic container
is the residual gap, and needs function monomorphization — deferred.

## 3. The mechanism — monomorphized destructors

For a drop of a value of monomorphic type `List P`, call a specialized
`axion_drop_List$P` instead of the generic `axion_drop_List`:
- `axion_drop_List$P` frees the `Cons` cell, frees the element field via `P`'s
  destructor (`axion_drop_P` if `P` needs deep drop, else a flat free), and recurses
  on the tail via `axion_drop_List$P`.
- It is generated by **substituting** the type parameter (`a := P`) in the generic
  `List` destructor template, resolving the now-concrete element field to a heap
  slot. Recursive: `List (Maybe P)` needs `axion_drop_Maybe$P`, which needs `P`.

This reuses the existing `gen_destructors` machinery, parameterized by an
instantiation.

## 4. What has to change (concretely)

1. **Carry the full type at drop sites.** Today `Term::Drop(name, Option<String>,
   …)` and `drop_ty` hold only the type **head** (`"List"`). Extend them to a
   monomorphic **key** that encodes the type arguments (`"List$P"`, `"List$Maybe$P"`
   — a mangling of `List P`). The full type is available:
   - **owned `%1` params:** directly from the function signature
     (`build_all_drop_ty` already reads `sig.param_types()` — it currently takes
     `head_con()`; take the whole `Type` instead).
   - **`Make`-bound locals** (`let x = Cons …`): the element type is not in the Core
     today (constructors carry no type args). Options: (a) infer it from the
     construction arguments' types (thread element types from inference), or (b) —
     simpler first cut — only monomorphize drops whose type comes from a signature,
     and keep the generic (leaky) destructor for `Make`-bound locals whose element
     type is unknown in Core. Ship (b), then (a).
2. **Generate the needed instantiations.** Collect the set of monomorphic keys that
   are dropped (`List$P`, …), close it recursively (each needs its element type's
   destructor), and generate one specialized destructor per key by substituting the
   type parameter in the template. Emit them alongside the generic ones.
3. **Route the drop.** `codegen`/`llvm` `Term::Drop` already forms the name
   `axion_drop_{ty}`; with the mangled key it becomes `axion_drop_List$P` — no
   backend change beyond the name.
4. **Keep the generic destructor** for uses where the element type is genuinely
   unknown (generic owning functions — the deferred gap): it stays leaky for the
   polymorphic field but correct for the spine (status quo, safe).

## 5. Verification (the gate)
- **ASan/LSan** (`scripts/sanitize.sh`): the new destructors must make
  `List P`/`List String`/nested cases **leak-free AND double-free-free**. Add
  fixtures with known `allocs == frees` (like `sum_payload`).
- **GHC oracle** (`scripts/differential.sh`): unchanged results.
- **Bench**: monomorphized destructors are the same shape as the generic one — no
  hot-path cost; confirm no regression.

## 6. Risk, phasing
- **Risk:** it is in the drop/reclamation path — the most memory-safety-critical
  code. Every increment must pass ASan/LSan before the next. (This session already
  showed how easy it is to introduce a double-free while editing drops.)
- **Phasing:**
  1. Thread the full type (mangled key) through `drop_ty` for **owned `%1` params**
     only; generic destructor unchanged elsewhere.
  2. Generate specialized destructors for the collected keys (single type parameter,
     one level: `List P`, `Maybe P`); ASan/LSan + oracle green; fixtures.
  3. Recurse for nested (`List (Maybe P)`) and multi-parameter (`Either a b`).
  4. `Make`-bound locals: thread element types from inference (closes the common
     non-`%1` case, e.g. the confirmed `List P` test).
  5. (Large, deferred) generic owning functions → needs function monomorphization.

## 7. Bottom line
The leak is real and general (any generic container of heap elements), rooted in the
uniform i64 representation (no runtime type tag). The fix is monomorphized
destructors — aligned with Axion's typeclass monomorphization, reusing
`gen_destructors`, with no backend change beyond the mangled name. It is a genuine
feature (type-threading + per-instantiation generation), memory-safety-critical, so
it is phased and ASan/LSan-gated at every step. Phase 1–2 close the common
signature-typed case; the generic-owning-function case is a deferred, larger gap
(function monomorphization).
